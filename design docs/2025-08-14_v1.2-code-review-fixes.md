# V1.2 代码审查修复

日期：2025-08-14

触发：`/code-review` 全量审查 v1.1 未提交改动，发现 8 项问题（含 2 个致命 bug），全部修复并验证。

---

## 修复 1 (致命): run() 一调用就崩溃

**问题**: `run()` 开头调用 `transition_to(THINKING)`，而刚构造/重置的 LoopController 状态已是 THINKING。v1.1 新增的状态转换白名单不含 `THINKING → THINKING`，导致每次 `run()` 都在第一行抛 ValueError，Agent 完全不可用。

**修复**: 移除该调用。`loop.reset()` 已把状态置为 THINKING，无需转换。在代码中留注释说明原因，防止后人再犯。

---

## 修复 2 (致命): STUCK 终止路径崩溃

**问题**: `record_action()` 触发 STUCK 时将状态置为 STUCK（终态），但 `_handle_acting()` 末尾无条件执行 `transition_to(THINKING)`。STUCK 的白名单为空 → ValueError，`_finalize()` 的"陷入死循环"分支永远不可达。

**修复**: 转换前检查 `if self.loop.status != AgentStatus.STUCK`，STUCK 时跳过转换，由主循环退出并交给 `_finalize()` 处理。

---

## 修复 3 (高): stuck_warnings 跨段累积

**问题**: 计数只在滑动窗口未满时清零。窗口满后，即使 Agent 已经跳出循环（执行了不同操作），计数器也不归零。之后任何无关的重复片段都会直接命中 STUCK 上限。

**修复**: 重构 `record_action()` —— 先判断窗口内是否全相同，不相同则清零计数并返回，相同才累计。

---

## 修复 4 (中): 全局环境变量污染

**问题**: 为避免 socks 代理报错，之前直接 `os.environ.pop(...)` 删除代理变量。这是全局进程级修改：需要代理才能访问 LLM API 的网络环境会全部超时，Agent 的 RunTerminal 工具启动的子进程也悄悄失去代理。

**修复**: 改用 `httpx.Client(trust_env=False)` 传给 OpenAI client。效果相同（httpx 不读代理环境变量），但不碰 `os.environ`，进程内其他代码不受影响。

---

## 修复 5 (低): thought 误提取

**问题**: `<thought>` 正则在整个原始文本上匹配。若 final_answer 的答案内容里恰好出现 `<thought>` 字样（如解释 XML 语法），会被误当作思考文本记入日志。

**修复**: 提取范围锚定为 action/final_answer 标签**之前**的文本片段（`raw_text[:match.start()]`）。

---

## 修复 6 (低): reset() 死代码

**问题**: `LoopController.reset()` 没有调用者（run() 每次新建实例）。

**修复**: 随修复 8 一并解决 —— `__init__` 中构造 loop，`run()` 中调用 `reset()`，reset() 成为活跃路径。

---

## 修复 7 (低): thought 类型死代码

**问题**: `ParsedOutput.thought_output()` 工厂方法无调用者，`agent.py` 中 `parsed.type == "thought"` 分支不可达（XMLParser 把纯 thought 转成 parse_error）。

**修复**: 接通该类型 —— XMLParser 遇到纯 thought（常见于 LLM 输出被截断）返回 thought 类型；Agent 收到后追加"请继续输出"提示并保持 THINKING 状态，不再计为格式错误。这是真实 Agent 处理输出截断的标准模式。

---

## 修复 8 (低): API 回归

**问题**: v1.1 后 `loop`/`logger` 在构造时为 None，`run()` 前访问 `agent.loop.status` 会 AttributeError。

**修复**: `__init__` 中即创建实例（配合修复 6），`run()` 里 `reset()` + 重建 logger。

---

## 验证

- 8 项修复全部有针对性测试（stub LLM 模拟 run()、STUCK 触发、计数清零、环境变量检查、正则锚定）
- 真实 API 冒烟测试通过：系统代理环境变量存在时连接正常（验证修复 4）

## 经验教训

1. **新增强校验（白名单）时，要全量回归所有调用点** —— 修复 1 是本轮审查引入的回归
2. **终态设计必须检查所有后续代码路径** —— 修复 2 的 STUCK 后无条件转换
3. **修改全局状态（环境变量）前先考虑作用域更小的方案** —— 修复 4 的 trust_env
4. **审查发现的两类 bug 分布**：致命 bug 来自最近一轮改动（v1.1），低危问题来自早期设计（v1.0）
