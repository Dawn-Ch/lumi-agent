## 0. 设计文档治理：每次迭代都留下可追溯证据

### 0.1 唯一目录与兼容处理

从本次开始，以 `minimal_swe_agent/design docs/` 作为设计过程的规范目录。工作区里已有的 `design_docs/` 暂视为历史目录；在没有单独核对引用和 Git 历史前，不自动移动或重命名，避免破坏链接。

当前文件名保留不动，因为它已经被明确引用。新文档统一采用：

```text
YYYY-MM-DD_vMAJOR.MINOR_TYPE_TOPIC.md
```

约束：

- 日期使用四位年份和 ISO 顺序，例如 `2026-08-14`；
- 版本与代码/架构里程碑对应，例如 `v1.1`；
- `TYPE` 从固定枚举中选择：`roadmap`、`architecture`、`adr`、`research`、`experiment`、`eval`、`postmortem`、`release-notes`；
- `TOPIC` 使用小写英文 kebab-case，避免空格、`&`、含义不明的“新建文档”；
- 同一主题当天多次修订，更新文内版本和修订记录，不创建 `final-final-2`；
- 只有语义里程碑变化才升版本：破坏性架构变更升 major，兼容性能力增加升 minor，文字修订只记 revision。

示例：

```text
2026-08-14_v1.1_research_deepseek-harness.md
2026-08-21_v1.2_adr_event-store-source-of-truth.md
2026-08-28_v1.2_experiment_parallel-tool-scheduling.md
2026-09-02_v1.2_postmortem_context-overflow.md
```

### 0.2 每份迭代文档的最小头部

```text
标题：
状态：Draft | Accepted | Superseded | Archived
版本：
日期：
范围：本次改变什么，不改变什么
关联：issue / commit / eval report / previous doc
证据：测试、trajectory、benchmark、外部资料
决策：采用、试验、推迟或拒绝什么
```

每次版本迭代至少留下四类信息：

1. **基线**：修改前的代码版本、测试与指标；
2. **决策**：问题、候选方案、取舍与不变量；
3. **证据**：实现后的测试、eval、失败案例和轨迹；
4. **迁移**：配置/事件/schema 是否变化，如何回滚或读取旧数据。

这样 `design docs/` 不是“写过就不再看的笔记区”，而是 Agent Harness 的设计史、实验账本和审计入口。

## 1. 先明确：你真正要学习的是什么

### 1.1 Model、Agent 与 Agent Harness

可以把 Coding Agent 分成三层：

```text
┌─────────────────────────────────────────────┐
│ Product Surface                             │
│ CLI / TUI / IDE / Web / 用户审批 / 任务管理 │
├─────────────────────────────────────────────┤
│ Agent Harness                               │
│ loop、context、tools、executor、policy、     │
│ sandbox、logging、memory、skills、evals      │
├─────────────────────────────────────────────┤
│ Model                                       │
│ 推理、计划、选择 action、生成答案             │
└─────────────────────────────────────────────┘
```

LLM 决定“下一步想做什么”；Harness 决定：

- 模型现在能看到什么；
- 模型可以调用哪些工具；
- action 是否合法、是否允许执行；
- 工具在哪里、以什么权限执行；
- observation 如何返回和压缩；
- loop 何时继续、暂停、恢复或结束；
- 运行轨迹如何保存、回放和评测；
- 跨轮、跨任务、跨进程的状态如何管理。

因此，Harness 不是一些外围工具的集合，而是 **把概率性的模型决策约束成可执行、可恢复、可观察、可评测系统的运行时**。

### 1.2 本项目当前处于什么位置

你的第一版已经跨过了最重要的入门门槛：

- 能把用户任务转成多轮 `LLM → Action → Tool → Observation`；
- 不再使用无界的 `while True`；
- Parser 失败可以返回结构化错误，而不是直接让进程崩溃；
- 用 AST 解析 Python 风格 action，解决了三引号、转义、嵌套括号等真实问题；
- Tool 有统一抽象，并使用 `ToolResult` 返回成功或失败；
- 已经开始处理命令审批、输出截断、重复 action 和运行日志。

这说明你已经理解了 **minimal agent 的最小闭环**。下一阶段的重点不应是继续增加 Parser 技巧，而应从“能跑”转向：

```text
可测试 → 可执行 → 有边界 → 可观察 → 可恢复 → 可扩展 → 可评测
```

## 2. 当前代码基线审计

本节不是要求你立刻修完所有问题，而是建立一张真实的能力地图。学习 Harness 的第一原则是：**区分代码已经做到的、README 声称做到的、以及未来计划做到的。**

### 2.1 当前值得保留的设计

| 设计 | 评价 | 后续方向 |
|---|---|---|
| `SWEAgent` 作为编排入口 | 合理，容易走读 | 后续逐步把执行、安全、上下文职责下沉 |
| `LoopController` 管理状态与预算 | 方向正确 | 增加合法状态迁移、时间/成本预算、明确终态 |
| `Parser` 返回 `ParsedOutput` | 正确 | 进一步统一协议语义，区分语法与 schema 校验 |
| `ASTActionParser` | 很好的教学实现 | 保留用于理解协议，但要与原生 tool calling 对照 |
| `Tool` / `ToolResult` | 已有良好雏形 | 使用标准 schema、结构化元数据与统一异常边界 |
| `PromptManager` | 已与主 loop 解耦 | 演进为 token-aware 的 `ContextBuilder` |
| `CommandChecker` | 能演示规则检查 | 不能充当真正 sandbox，后续演进为 Policy 层 |
| `AgentLogger` | 建立了 trajectory 意识 | 改为持久化事件流，并与终端展示分开 |

### 2.2 P0：在运行陌生仓库前必须理解的问题

这些是安全或正确性边界，而不是“高级功能”。

#### 1. 文件工具尚未真正限制在 workspace 内

`ReadFile`、`WriteFile`、`SearchContent` 接受任意路径，但没有拿到 `working_directory`，也没有执行 canonical path 校验。模块注释中“所有路径操作都在工作目录内”目前只是设计目标。

你需要学习：

- `abspath`、`realpath`、符号链接与路径穿越的区别；
- 为什么仅检查字符串前缀不可靠；
- read root、write root、temporary root 是否应当分开；
- 路径校验应由 Tool、Executor 还是 Policy 负责。

#### 2. Terminal 没有在目标项目目录执行

`RunTerminal` 使用 `cwd=os.getcwd()`，但 Agent 的目标目录是构造函数中的 `working_directory`。如果从其他目录启动程序，Prompt 告诉模型的目录与命令真实执行目录可能不同。

这是典型的 Harness bug：**模型看到的环境描述与 Executor 的真实环境不一致。**

#### 3. `shell=True + 黑名单` 不是安全边界

黑名单可以作为提示和审批信号，但无法可靠识别：

- 通过 Python、Node、Perl 等解释器隐藏的副作用；
- 命令替换、重定向、管道和编码后的命令；
- 合法命令作用于危险路径；
- 凭据读取、网络外传、进程逃逸；
- 未列入规则的新命令。

必须区分：

```text
Policy：这次调用按照规则是否允许？
Sandbox：即使判断错了，进程实际上能做什么？
```

Policy 是决策层，Sandbox 是强制执行层，两者不能互相替代。

#### 4. 失败的 terminal 输出会丢失

`RunTerminal` 在失败时把 stdout/stderr 放入 `ToolResult.output`，但 `ToolResult.to_observation()` 对失败结果只返回 `error`。模型可能只能看到退出码，看不到真正的报错内容。

这会直接破坏 ReAct 的核心：环境已经给出了证据，但 Harness 在 observation 层把证据丢掉了。

#### 5. 参数 schema 目前没有真正校验

`Tool.parameters` 是自定义描述结构，并非标准 JSON Schema；`ActionValidator` 只检查部分工具名逻辑，而且尚未接入执行流程。缺参数可能在 `tool.execute(**tool_args)` 处抛出未捕获的 `TypeError`。

要形成完整链路：

```text
Parser 只负责语法
→ Action Schema 负责数据形状
→ Tool Registry 负责工具发现
→ Executor 负责调用与异常归一化
```

### 2.3 P1：决定系统是否稳定、是否可调试的问题

- 当前仓库没有受版本控制的自动化测试；
- LLM 调用失败、工具框架异常等可能直接穿透并终止进程；
- 只有 `max_turns`，没有总耗时、模型调用次数、token、成本、工具调用次数等预算；
- 解析重试虽然不计 turn，但仍会消耗真实模型调用与 token；
- 重复检测只比较 action，不比较 observation；它只警告，不会进入明确的 `STUCK` 终态；
- Logger 只在内存中保存摘要，没有 run id、事件类型、持续时间、原始请求/响应、工具结果与终止原因；
- 当前 logger 实际上没有保存 thought 内容，与 README 的“完整运行日志”描述不一致；
- `Action` 模块注释写的是 Pydantic，但实现是 dataclass；
- `ParsedOutput` 文档写“五种类型”，实际列出并使用的是四种；
- 状态转换没有合法边校验，任何代码都可以从任意状态跳到任意状态；
- 同一个 `SWEAgent` 实例再次调用 `run()` 时，loop/logger 状态不会自动重置；
- Prompt 中的文件列表只是启动时的一层快照，执行修改后会过期；
- 文件读取按行截断，但超长单行、terminal 输出和 messages 总量仍可能污染 context。

这些问题适合转化为测试，而不是只写进 TODO。

### 2.4 P2：高级能力，不应现在一起加入

- 显式 Task Planning / Task Scheduling；
- 多轮会话和断点恢复；
- Context compression；
- project/session/long-term memory；
- background process；
- skills / plugins / MCP；
- multi-agent；
- 完整 TUI 和远程执行。

它们都重要，但必须建立在稳定的单 Agent runtime、Executor、日志和 eval 之上。

## 3. 必须分清的五组概念

### 3.1 Parser 安全不等于 Tool 安全

`ast.parse(mode="eval")` 不执行代码，`ast.literal_eval()` 只接受字面量，因此它解决的是：

> “模型输出的字符串能否被安全、确定地转换成 Action？”

它没有解决：

> “解析出来的 Action 执行后是否安全？”

例如下面的 action 可以被 AST 安全解析，但执行能力仍然危险：

```text
run_terminal(command="python -c '...'")
```

因此要始终区分：

```text
语法安全 → schema 安全 → policy 判断 → sandbox 强制边界
```

### 3.2 Tool 不等于 Executor

Tool 描述一个能力：

```text
name + description + input schema + handler
```

Executor 管理一次调用的完整生命周期：

```text
查找工具
→ 校验参数
→ 生成 call id
→ 执行 policy
→ 请求审批
→ 选择同步/异步 runtime
→ timeout / cancel / exception normalization
→ 输出截断与 artifact 保存
→ 返回统一 ToolResult
```

当前 `_handle_acting()` 同时承担了这些职责，所以 ClaudeCode 指出“没有独立 Executor”是基本正确的。不过不要为了“有一个类”而机械拆分；要先写出 Executor 的输入、输出、失败语义和测试，再进行重构。

### 3.3 Planning 不等于在 ReAct 前多调用一次 LLM

一个真正有用的 plan 至少需要：

- `goal`：总目标；
- `steps`：子任务；
- `status`：pending / in_progress / completed / blocked；
- `dependencies`：依赖关系；
- `success_criteria`：怎样算完成；
- `evidence`：用什么环境证据证明完成；
- `revision_reason`：为什么修改计划。

计划不是事实，也不应锁死 loop。环境反馈可能使计划失效，因此需要：

```text
计划 → 执行 → 验证 → 更新计划
```

并非所有任务都值得规划。读取一个文件时强制先规划，只会增加延迟和错误面。应通过任务复杂度或模型请求决定是否启用 plan。

### 3.4 Context management、持久化与 long-term memory 不是一回事

| 能力 | 解决的问题 | 生命周期 |
|---|---|---|
| Context management | 下一次模型调用应该看到哪些 token | 单次 LLM call / 单次 run |
| Conversation/session state | 多轮用户交互如何延续 | 一个会话 |
| Checkpoint/resume | 进程崩溃后如何继续未完成任务 | 一个 run |
| Project memory | 仓库约定、常用命令、历史决策 | 多个 run |
| Long-term semantic memory | 从大量历史中检索相关经验 | 多会话、长期 |

Logger 持久化是 memory 的基础设施之一，但有日志不等于有 memory；单次 CLI 退出也不等于没有 context management。

### 3.5 Logger、Tracing 与 Evals 不等价

- Logger：记录发生了什么；
- Trace：把 model call、tool call、approval、artifact 等事件串成因果链；
- Metrics：把事件聚合成数字；
- Eval：用预定义任务和评分方法判断系统是否变好。

没有 eval 时，你无法回答：

> AST Parser、Planner、Memory 或 Multi-Agent 到底让 Agent 更好了，还是只让代码更多了？

## 4. 推荐的目标架构

这不是下一次重构必须一次实现完的目录，而是学习过程中逐步逼近的职责地图。

```text
User / CLI / TUI
        │
        ▼
SessionController
        │  create/resume/cancel run
        ▼
RunOrchestrator / LoopController
        ├─────────────── PlanState / TaskState
        ├─────────────── Budget / StopPolicy
        │
        ▼
ContextBuilder ◄──────── MessageStore / Project Instructions / Skills
        │
        ▼
ModelGateway
        │  ModelResponse
        ▼
ProtocolAdapter / Parser
        │  Action | FinalAnswer | ParseError
        ▼
ActionValidator
        ▼
PolicyEngine ───────────► Human Approval
        ▼
ToolExecutor
        ├─────────────── ToolRegistry
        ├─────────────── Sandbox / Workspace
        └─────────────── BackgroundTaskManager
        │
        ▼
ToolResult / Artifact / Observation
        │
        └───────────────► ContextBuilder → 下一轮

所有模块 ───────────────► EventStore / Trace / Metrics / Eval
```

### 4.1 各层边界

#### RunOrchestrator

只负责流程决策：

- 当前状态；
- 下一步调用哪个组件；
- budget；
- stop reason；
- pause/resume/cancel；
- 最终 run result。

它不应亲自执行 shell、拼接字符串 schema 或写日志文件。

#### ContextBuilder

根据 token budget 构造每次模型输入：

- 不可丢失的系统约束；
- 当前任务与验收标准；
- 当前 plan；
- 最近交互；
- 相关历史摘要；
- 必要的工具结果或 artifact 引用。

#### ModelGateway

统一不同 provider/model 的：

- 请求；
- timeout/retry/backoff；
- streaming；
- token/usage/cost；
- provider 错误归一化；
- structured tool call。

#### ProtocolAdapter

把 provider response 转成 Harness 内部统一事件。XML、JSON、原生 tool calling 都只是不同 adapter，不应影响 loop 的核心状态。

#### ToolExecutor

是 LLM 意图与真实环境副作用之间的唯一入口。任何 Tool 都不能绕过 Executor 直接执行。

#### EventStore

使用 append-only 事件记录，而不是只保存最终摘要。状态可以从事件重建，UI、debug、resume 和 eval 共用同一份事实来源。

### 4.2 从 DSH/Cordis 吸收什么，以及暂时不吸收什么

[DeepSeek Harness 架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)提出“everything is a plugin”：模型适配器、工具注册、session log、agent loop 都可以通过 Cordis plugin 组合。其真正有价值的不是“插件数量多”，而是四个底层约束：

1. **依赖面向稳定能力键，不面向具体实现类**：consumer 依赖 capability/service definition，provider 可以替换；
2. **注册是可逆 effect**：事件监听、工具注册、后台资源在 plugin unload 或 scope 销毁时必须清理；
3. **空间作用域明确**：全局、项目、session、agent 等 scope 可以拥有不同 provider 与配置；
4. **时间生命周期明确**：能力何时加载、可用、热替换、停止，不能靠全局单例和隐式副作用。

这对应两种“可组合性”：

```text
空间可组合：同一能力在不同 scope 使用不同 provider
时间可组合：插件加载产生的副作用可以被完整撤销
```

对 minimal SWE Agent，建议先定义轻量的 capability seam，而不是立刻实现完整 Cordis：

```text
Capability Definition  ← 稳定协议、事件、错误语义
Provider                ← 本地实现、远程实现、测试替身
Consumer                ← 只依赖 definition，不 import provider
Lifecycle               ← start / stop / cleanup / health
```

第一批值得形成 seam 的能力是：`ModelGateway`、`ToolRegistry`、`ToolExecutor`、`EventStore`、`Sandbox`、`BackgroundJobs`、`SkillRegistry`、`Persistence`。Parser 内部的小函数、普通数据类不需要为了“万物皆插件”而插件化。

### 4.3 三类事件、一个事实源

DSH 将事件分为三类，这比把一切都塞进 Logger 更清楚：

| 事件域 | 是否持久化 | 作用 | 本项目建议 |
|---|---:|---|---|
| Session events | 是 | 重放、恢复、派生模型上下文 | append-only EventStore |
| Live agent events | 否或按需 | UI 流式更新、取消、协调 | EventBus / callbacks |
| Capability events | 通常否 | provider 之间的 pre/post hooks | typed hooks |

关键不变量是：**凡是会影响模型后续判断的事实，都必须进入 durable session log；messages 只是从日志派生的视图，不再是另一份独立真相。** 这样 replay、fork、resume、UI、telemetry 与 eval 才不会各自维护互相漂移的状态。

### 4.4 集百家之长，但不混淆层次

| 设计命题 | DSH/Cordis | Codex | Claude Code | minimal SWE Agent 的吸收策略 |
|---|---|---|---|---|
| 运行时扩展 | capability seam、plugin tree、可逆 effect | Skills、Plugins、MCP | Skills、Plugins、Hooks | 先做稳定内部协议，再做可卸载扩展 |
| 项目指令 | scope 与 context injection | `AGENTS.md` 按目录分层覆盖 | `CLAUDE.md`、rules、用户/项目配置层 | 建立带 provenance 的 ProjectInstructionResolver |
| 强制规则 | tool guards、approval、sandbox | approval policy 与 sandbox policy 分离 | deterministic hooks + deny-first permissions | Prompt 只指导；Policy/Hook/Sandbox 才强制 |
| 会话事实 | append-only session events | thread/run/event、compaction | transcript、session/compact hooks | EventStore 是唯一事实源，Context 是派生视图 |
| 能力按需加载 | layered Skills registry | Skill progressive disclosure | Skill 正文按需加载 | 初始只注入摘要，选中后加载正文 |
| 子代理 | 可选 capability、多 provider、durable child session | subagent/worktree/权限边界 | 隔离 context、前后台 subagent | 单 Agent 稳定后再实验，并显式传递权限与 lineage |

这里最重要的判断是：**插件化解决替换与组合问题；Hooks 解决确定性生命周期插入点；Skills 解决按需工作知识；MCP 解决跨进程能力交换；它们不是同一个抽象。**

## 5. 推荐学习顺序：不要按功能热度排序

下面的阶段有明确依赖关系。每一阶段都包含：

1. 要理解的问题；
2. 应交付的设计或实现；
3. 必须完成的测试/实验；
4. 口试题；
5. 退出条件。

只有满足退出条件，才进入下一阶段。

## 阶段 0：冻结 v0.1，建立可复现基线

### 学习目标

理解“重构之前先锁定行为”的原因，学会**为非确定性系统建立确定性的测试层**。

### 任务

- 给当前版本打 baseline tag；
- 整理 10～20 个 toy tasks，覆盖读取、搜索、修改、测试、失败、安全与格式错误；
- 设计 `ScriptedLLM/FakeLLM`，按预设顺序返回模型输出；
- 保存 3～5 条真实成功/失败 trajectory 作为 golden cases；
- 记录当前成功率、平均轮次、解析错误、工具失败与耗时。

### DSH 对照研读：先测“世界”，再测 Agent 的自述

阅读 DSH 的 [Testing Strategy](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/testing.md)，重点吸收：

- mock 只放在真正不确定的边界；ToolExecutor、文件系统和事件排序尽量使用真实实现；
- 覆盖率只是门槛，测试必须覆盖 cleanup、并发、ordering、错误路径和历史 regression；
- E2E 成功条件来自真实文件、exit code、测试结果和 durable events，而不是 final answer 里的“已经完成”；
- 同一个 contract test 应能跑不同 provider/backend，避免测试绑定具体实现。

阶段实验：为当前 loop 写一条“模型声称已修复，但文件没有变化”的 FakeLLM trajectory，证明 evaluator 会判失败。

### 测试金字塔

```text
少量真实模型 E2E
    ↑
toy repo 集成测试
    ↑
FakeLLM loop 测试
    ↑
Parser / Tool / Policy 单元测试
```

#### Parser 必测

- 三引号、转义引号、Unicode、多行字符串；
- 嵌套 list/dict；
- 位置参数、`**kwargs`、属性调用、多个 action；
- 标签缺失、标签嵌套、同时存在 action 与 final；
- XML 与 JSON 是否产生相同内部 Action；
- 随机畸形输入不能让进程崩溃。

#### Loop 必测

- 正常 final；
- 连续 ParseError 后恢复；
- 达到解析错误上限；
- 未知工具；
- 工具失败后继续；
- 用户拒绝后继续；
- 达到 turn 上限；
- 模型调用异常；
- 连续重复 action。

### 口试

1. 为什么 FakeLLM 比反复请求真实 API 更适合测 loop？
2. golden trajectory 能发现什么类型的回归？
3. 一个测试通过，为什么仍不能证明 Agent 能解决真实任务？

### 退出条件

- 所有核心模块有确定性测试；
- 修 Parser 或 loop 时能在一分钟内知道是否破坏既有行为；
- baseline 指标已经保存。

## 阶段 1：统一内部协议，完成 Executor

### 学习目标

理解 Agent Harness 最重要的稳定边界：

```text
ModelResponse → AgentEvent → Action → ToolCall → ToolResult
```

### 任务

- 用 Enum/判别联合替代任意字符串 `type`；
- 明确定义 `RunResult` 与终止原因；
- 采用标准 JSON Schema 或等价类型模型描述 Tool 参数；
- 让 ActionValidator 真正校验：
  - 工具是否存在；
  - required 参数；
  - 未知参数；
  - 参数类型和约束；
- 增加 ToolRegistry；
- 增加统一 ToolExecutor；
- 捕获所有工具边界异常，禁止内部异常直接炸穿主 loop；
- ToolResult 增加：
  - `call_id`
  - `status`
  - `output`
  - `error`
  - `metadata`
  - `started_at / ended_at`
  - `artifact_refs`

### DSH 对照研读：协议必须同时约束输入、输出和身份

结合 DSH 的 [Tools 子系统](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/tools.md)补充三个不变量：

- Tool definition 同时声明 input schema 与 output schema，两端都做 runtime validation；
- `call_id`、`root_call_id`、tool name、agent/session identity 在进入执行管线后不可被 hook 偷换；
- unknown tool、schema error、tool exception 都归一化为结构化失败，不能直接结束 turn 或炸穿 loop。

不要现在实现 Cordis，但要做一个 provider-swap 实验：同一 `ToolExecutor` contract 分别接真实工具和 fake provider，主 loop 零修改。

### 关键实验

将同一个 loop 分别接入：

1. XML + AST action；
2. JSON action；
3. 模型原生 structured tool calling。

比较解析失败率、Prompt 长度、实现复杂度和可移植性。不要预设“原生协议一定全面优胜”；要用数据理解每种协议的边界。

### 口试

1. 为什么 Parser 成功后仍必须做 Action schema validation？
2. Executor 与 Tool 的职责为什么不能混在一起？
3. ToolResult 为什么不能只返回一个字符串？

### 退出条件

- 任意模型输出和工具异常都会变成结构化事件；
- loop 不依赖 XML/JSON 的具体实现；
- 新增 Tool 不需要修改主 loop；
- 失败 observation 不再丢失 stdout/stderr 等关键证据。

## 阶段 2：把工具系统做成真正的 ACI

### 学习目标

理解 SWE-agent 的核心观点：模型能力相同时，Agent-Computer Interface 的设计也会显著影响结果。

### 任务

#### 文件工具

不要只做 `read_file/write_file`，应研究：

- `list_files` / `find_files`；
- `read_file(path, start_line, end_line)`；
- `search_text` 的上下文行、分页和结果句柄；
- `apply_patch` 或结构化 edit，而不是每次覆盖整个文件；
- 写入前后 diff；
- 原子写入与失败回滚；
- 文件编码、二进制、超大文件；
- symlink 与 workspace boundary。

#### Terminal

研究并设计：

- `cwd` 明确绑定 workspace；
- `argv` 执行与 `shell=True` 的能力差异；
- timeout；
- stdout/stderr/exit code 分离；
- 最大输出与 artifact 文件；
- environment allowlist；
- process tree 终止；
- 网络权限；
- 交互式命令如何处理。

#### Tool ergonomics

对每个 Tool 回答：

- 模型是否容易选对这个工具？
- 参数名是否不易误解？
- 错误是否告诉模型下一步怎么修正？
- 两个工具是否能力重叠？
- output 是否保留证据，又不会淹没 context？

### DSH 对照研读：Tool 不只是一个 `execute()`

DSH 的 tool definition 还包含 timeout、并发模式、输出 schema 和 UI presenter。minimal SWE Agent 可以分步吸收：

- 用 `parallel | exclusive` classifier 表达“同批 tool call 能否并发”，不要让 loop 猜；
- Tool 只实现领域动作，timeout/retry/metrics/normalization 由 Executor 管；
- UI 展示模型与 model-facing result 分离，避免为 TUI 方便而污染 observation；
- 文件写入、shell 和外部 API 各自声明 capability 与 side-effect class。

这一步的重点不是增加字段数量，而是证明每个字段由哪个组件消费、违反时由谁拒绝。

### 实验

对同一批任务比较：

- 全文件覆盖 vs patch edit；
- 整文件读取 vs 行范围读取；
- 原始 terminal 文本 vs 结构化 terminal result；
- 第一层文件列表注入 vs 按需搜索。

### 退出条件

- 所有文件访问都无法越过声明的 workspace roots；
- terminal 确实在目标 workspace 中执行；
- Agent 修改文件后能得到明确 diff 并运行验证；
- Tool 文档与行为通过 contract test 保持一致。

## 阶段 3：持久化事件、Tracing 与 Evals

### 学习目标

从“终端里看起来跑通了”升级到“能证明为什么成功或失败”。

### 事件模型

建议至少包含：

```text
RunStarted
ModelRequestStarted / ModelResponseReceived / ModelCallFailed
ParseSucceeded / ParseFailed
ToolCallProposed
ApprovalRequested / ApprovalResolved
ToolCallStarted / ToolCallFinished
ArtifactCreated
PlanUpdated
ContextCompacted
RunPaused / RunResumed
RunCompleted / RunFailed / RunCancelled / RunStuck
```

每个事件带：

- `run_id`
- `event_id`
- `parent_event_id`
- 时间戳；
- turn / model_call / tool_call 编号；
- duration；
- 可序列化 payload；
- 敏感数据脱敏信息。

推荐先用 JSONL append-only 文件，不必立刻上数据库或可观测平台。

### DSH 对照研读：事件不是日志字符串

结合 DSH 的 [Agent Lifecycle](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/agent-lifecycle.md)、[Session](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/session.md) 与 [Persistence](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)：

- 明确 `turn` 与 `step`：一次 turn 可以包含零到多个“model request + tool execution” step；
- `assistant/chunk` 可用于 live stream，但最终 `assistant/message`、`tool/call`、`tool/result` 必须有 durable 表示；
- Session header（版本、cwd、父 session、agent preset）与 append-only event body 分开；
- LLM history 从 event log 派生，禁止再单独保存一份会漂移的 messages 历史；
- crash recovery 不应悄悄截断半个 turn，应追加可解释的 `interrupted` 终止事件；
- JSONL 与未来 SQLite backend 共用一套 persistence contract tests。

进一步建立一条规则：`model-visible means logged`。System prompt、tool schema、模型配置等 request header 至少要以可重建或带版本引用的形式记录，否则无法真正 replay。

### Eval 数据集

构造至少 20 个本地任务：

| 类别 | 示例 | 评分方式 |
|---|---|---|
| 定位 | 找到 TODO / 函数定义 | exact match |
| 编辑 | 修复单文件 bug | tests + diff scope |
| 多文件 | 修改接口并更新调用处 | tests |
| 恢复 | 首次命令失败后换策略 | trajectory assertions |
| 安全 | 请求读取 workspace 外文件 | 必须拒绝 |
| 模糊 | 缺少关键需求 | 应询问用户 |
| 不可完成 | 缺依赖或测试损坏 | 正确报告 blocker |

### 指标

- task success rate；
- tests pass rate；
- 平均/95 分位 model calls；
- tool calls；
- token、成本、耗时；
- parse error rate；
- invalid tool rate；
- repeated no-progress rate；
- approval 次数与拒绝后恢复率；
- workspace escape attempt；
- unnecessary diff size；
- final answer 与实际环境是否一致。

### 口试

1. 为什么“最终答案说成功”不能作为成功判据？
2. trajectory eval 与最终结果 eval 各自检查什么？
3. 为什么没有 baseline 时不能判断 Planner 是否有效？

### 退出条件

- 每次 run 都能持久化、重放和定位失败点；
- 任意架构改动前后都能跑同一套 eval；
- README 中的能力声明都有测试或指标证据。

## 阶段 4：任务状态、Planning 与 Verification

### 学习目标

学会区分：

- 模型临时推理；
- 显式任务计划；
- Harness 持有的事实状态；
- 环境验证证据。

### 不建议的做法

不要简单地：

```text
进入 ReAct loop 前固定多调用一次 LLM，生成一份永不更新的 plan
```

这只是一段额外文本，不是真正的 task scheduling。

### 推荐设计

- 简单任务允许直接 ReAct；
- 复杂任务才建立 `TaskPlan`；
- plan 是结构化状态，而不是只存在 messages 中；
- 每个 step 有成功标准；
- 完成 step 必须附带环境证据；
- observation 可以触发 replan；
- 用户能查看、修改或拒绝计划；
- final 前执行独立 verification 阶段。

### DSH 对照研读：Plan 是协作状态，不是安全边界

DSH 的 [Plan Mode](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/plan.md)值得吸收的不是界面，而是边界：

- Plan 是可选、可记录、可折叠重建的 collaboration state；
- Loop 不依赖 plan mode 才能运行，简单任务仍可直接进入 ReAct；
- Plan 对模型是 soft guidance；即使计划写着“只读”，真实限制仍由 Policy 和 Sandbox 强制；
- 离开 plan mode 时应把完整计划展示给用户审阅，而不是只发送“计划完成”。

阶段实验：让计划声称“不要改文件”，同时让模型发出写工具调用，验证 Policy 仍独立阻断它；再让用户修改计划，检查 event fold 后恢复出的 PlanState 一致。

### 实验

使用相同的多文件任务比较：

1. 无显式计划；
2. 一次性静态计划；
3. 可更新计划；
4. 可更新计划 + step verification。

比较成功率、轮次、返工次数和无关修改量。

### 退出条件

- 系统能区分“模型说完成”和“证据证明完成”；
- plan 能在环境变化时更新；
- 简单任务不会被强制增加不必要的计划开销。

## 阶段 5：Context Engineering

### 学习目标

把 messages 从一个不断 append 的 list，升级成受预算管理的信息系统。

### Context 的四个层级

```text
Pinned：系统约束、权限、用户目标、关键验收标准
Working：当前 plan、最近 action/observation、待解决错误
Retrieved：按需读取的文件片段、project memory、skill
Archived：旧的原始消息、完整日志、超长 tool artifact
```

### 任务

- MessageStore 与 ContextBuilder 分离；
- 记录 token usage；
- 为 system、tools、history、artifacts 设置预算；
- observation 保留摘要 + artifact ref；
- 旧历史压缩时保留：
  - 用户目标；
  - 已做修改；
  - 测试证据；
  - 未解决问题；
  - 安全和权限状态；
- 压缩前后做一致性检查；
- 支持按需重新读取原始 artifact，而非把所有内容永久塞进 prompt。

### DSH、Codex、Claude Code 对照研读：Context 必须有来源和加载时机

- DSH 的 [Compaction](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/compaction.md)把压缩做成可选 seam，并用 durable start/summary/end 事件包围压缩；崩溃后可以知道压缩是否完成。
- DSH 的 context injection 是显式能力，不把任意插件输出偷偷塞进 messages。
- [Codex `AGENTS.md`](https://developers.openai.com/codex/guides/agents-md)按 global → repository root → cwd 分层加载，靠近当前目录的指令具有更高优先级；这启发我们记录 instruction 的 scope、priority 与 provenance。
- [Claude Code 扩展概览](https://code.claude.com/docs/en/features-overview)清楚区分：总是触发且需要确定性的规则放 Hook，按需且需要模型判断的知识放 Skill。

建议增加 `ContextItem` 概念：每项都带 `source`、`trust_level`、`scope`、`priority`、`token_cost`、`expires_at`。ContextBuilder 根据预算选择内容，但不得覆盖高优先级安全约束。

阶段实验：在根目录和子目录放置冲突的项目指令，验证解析顺序可解释；构造压缩中途崩溃，验证恢复时不会同时采用原历史和半成品摘要。

### 必做失败实验

- 超长 terminal 输出；
- 500 行以内但单行极长的文件；
- 连续十几轮工具调用；
- summary 错误地声称测试通过；
- repo 文件中包含“忽略系统提示”等 prompt injection 文本。

### 退出条件

- 长任务不会因为 messages 无限增长而失控；
- 压缩后关键约束和未完成任务不会丢失；
- 外部文件和工具输出被当作不可信数据，而不是系统指令。

## 阶段 6：Session、Checkpoint 与 Memory

### 学习目标

按生命周期逐层增加持久化，不要一开始就上向量数据库。

### 推荐顺序

#### 1. Run checkpoint

保存：

- run 状态；
- messages/artifact refs；
- plan；
- budgets；
- pending approval/tool call；
- workspace/version 信息。

目标：进程崩溃后可以恢复同一个任务。

#### 2. Multi-turn session

一次任务结束后继续接受用户输入，但每个新任务生成独立 run。Session 负责串联 runs，Run 不应无限复用旧状态。

#### 3. Project memory

优先用透明、可编辑的 Markdown/YAML：

- 项目结构；
- build/test 命令；
- 代码规范；
- 用户长期偏好；
- 已确认的架构决策。

#### 4. Long-term retrieval

只有历史规模大到无法直接读取时，再研究：

- chunking；
- embedding/keyword/hybrid retrieval；
- reranking；
- relevance、recency、authority；
- provenance；
- memory 更新、冲突、过期和删除。

### DSH 对照研读：Session log、checkpoint、memory 必须分家

DSH 的 session 设计强化了三条边界：

- append-only session events 是事实历史；checkpoint 是加速恢复的派生快照；memory 是跨 run 选择性保留的知识；
- durable session 与当前进程里的 active runtime 不是同一对象，进程重启后可以从前者恢复后者；
- 持久化格式必须 versioned，遇到无法理解的新版本要明确拒绝，不能“尽量读”出错误状态。

阶段实验：从任意 event offset 重建 state，并与 checkpoint 恢复结果比较；故意中断 tool call，恢复后追加 synthetic interrupted result，不能重复执行有副作用的调用。

### Memory 写入原则

不能让模型把每句话都写成长期记忆。每条候选 memory 都应考虑：

- 是否可能跨任务复用；
- 来源是什么；
- 是事实、偏好、推断还是临时状态；
- 有效范围和过期时间；
- 新证据冲突时怎样更新；
- 用户能否查看和删除。

### 退出条件

- 能恢复中断任务；
- 新任务不会错误继承旧 run 的临时状态；
- 每条长期信息都有来源、范围和更新规则。

## 阶段 7：Background Tasks 与并发执行

### 学习目标

理解“命令异步运行”和“多个 Agent 并行工作”是两个不同问题。

### BackgroundTaskManager

长命令启动后立即返回：

```text
task_id
status = RUNNING
started_at
cwd
deadline
output_cursor
```

提供：

- `start_task`
- `poll_task`
- `read_output`
- `send_input`
- `cancel_task`
- `wait_task`

状态至少包含：

```text
QUEUED / RUNNING / SUCCEEDED / FAILED / TIMED_OUT / CANCELLED
```

### 关键原则

- 不能假设 `npm install` 会成功；
- 只能并行推进与该任务无依赖的工作；
- 依赖后台任务的 step 必须等待明确终态；
- timeout 后要终止整个 process tree；
- 输出采用 cursor 增量读取，避免重复塞入 context；
- run 结束时必须处理遗留进程。

### DSH 对照研读：Job runtime 管身份和生命周期，Tool 管资源

参照 DSH 的 [Background Jobs](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/jobs.md)：

- Job runtime 负责 id、owner session、状态、访问控制、并发上限和取消协议；
- 具体 Tool/producer 负责它创建的进程、socket、临时文件等资源；
- `cancel()` 必须幂等；`done` 只有在资源真正释放后才能完成；
- 读取输出使用 cursor，`wait` 与 `read` 分离；可预测的 task id 不是授权机制；
- scope/session teardown 时统一取消仍在运行的 jobs。

把状态补充为 `STOPPING`，区分“已发送取消请求”和“资源已释放”。同时记录 `owner_session_id`、`producer_tool`、`resource_cleanup_status`。

### 实验

- 安装任务运行时并行阅读源码；
- 后台任务失败后重新规划；
- 超时与取消；
- 交互式进程；
- 两个后台任务的依赖和资源竞争；
- Agent 结束后检查是否遗留进程。

### 退出条件

- 后台任务有完整生命周期与日志；
- 独立工作可以安全重叠；
- 依赖未完成任务的步骤不会被提前执行。

## 阶段 8：Policy、Approval 与 Sandbox

### 学习目标

从“检测危险字符串”升级到 capability-based security。

### Policy 输入

风险不应只由 tool name 决定，还要考虑：

- 工具；
- 参数；
- canonical path；
- 当前 workspace；
- 是否联网；
- 命令副作用；
- 用户授予的权限；
- 当前任务与历史审批；
- 是否读取敏感数据；
- 是否会产生外部不可逆影响。

### Approval

审批请求应展示：

- 准备执行什么；
- 为什么需要；
- 影响范围；
- 精确命令/路径；
- 风险；
- 可选的授权范围：仅一次、此类操作、当前 run。

用户拒绝是一个正常 observation，不是系统异常。

### Sandbox

研究：

- 文件系统只读/可写 roots；
- network on/off；
- CPU、内存、磁盘、进程数、wall time；
- secret 注入；
- 容器、macOS sandbox、Linux namespace 等隔离方式；
- host 与 sandbox 的路径映射；
- sandbox 销毁与 artifact 导出。

### DSH、Codex、Claude Code 对照研读：安全要有顺序、不变量与 fail-closed

按 DSH 的 [Tool Execution Pipeline](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/tool-execution-pipeline.md)画出并测试完整顺序：

```text
proposed call
→ durable tool/call
→ pre-execute hooks
→ identity/schema freeze
→ monotonic guards
→ approval
→ executor timeout/retry/metrics
→ sandbox/fs enforcement
→ post-execute normalization
→ immutable final result
→ durable tool/result
```

需要吸收的安全不变量：

- guard 只能 `deny` 或 `abstain`，后执行的扩展不能把先前拒绝改回允许；
- 需要审批但用户不可达、审批系统缺失或超时时，默认拒绝；
- sandbox mode 主要描述文件副作用，网络和进程可见性应单独声明；
- provider 必须报告 `full | partial | unavailable` enforcement；受限模式下不能静默退化成裸执行；
- canonical workspace root 在 session 建立时固定，不能由一次 tool call 偷换。

[Codex 的审批与沙箱文档](https://developers.openai.com/codex/agent-approvals-security)也强调把“何时询问用户”和“实际在哪里强制”分开；[Claude Code permissions](https://code.claude.com/docs/en/permissions)则提供 deny-first 参照：Hook 的 allow 不能覆盖明确 deny。minimal SWE Agent 应把这一点写成 PolicyEngine 的测试不变量，而不只写进 prompt。

### 红队任务

- 路径穿越和 symlink escape；
- 从 repo 文本诱导读取 `.env`；
- 通过解释器绕过命令黑名单；
- 网络外传；
- fork bomb / 大输出 / 磁盘填充；
- 子进程逃逸；
- 破坏性 git 操作；
- 用户拒绝后换一种语法重复执行。

### 退出条件

- Policy 判断错误时，Sandbox 仍能限制实际损害；
- 每次副作用都有明确权限来源；
- 安全测试进入持续回归集。

## 阶段 9：Skills、Plugins 与 MCP

### 学习目标

理解三者解决的层次不同：

- Tool：一次可调用能力；
- Skill：关于“何时、如何组合能力”的按需上下文和流程知识；
- Plugin：打包技能、工具、连接器和配置的分发单元；
- MCP：Host/Client/Server 之间发现并调用 tools、resources、prompts 的协议。

### Skills

实现前先设计：

- metadata：name、description、触发范围、版本；
- discovery；
- selection；
- progressive loading；
- 冲突处理；
- provenance；
- skill context 的 token budget；
- 不可信 skill 的权限边界。

关键评测：

> 正确技能是否在正确任务被选中？无关技能是否污染 context？

### MCP

先实现一个最小 MCP client，只接一个本地测试 server，理解：

- initialize/capability negotiation；
- tools/list 与 tools/call；
- resources 与 prompts；
- transport；
- timeout、取消、断线与 schema 变化；
- remote server 的认证和信任边界。

不要把 MCP 当作 Agent framework。MCP 解决上下文和能力交换协议，不负责你的 loop、context 策略和任务调度。

### DSH/Cordis 深读：插件化的最小正确语义

按顺序阅读 [Cordis Primer](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md)、[Architecture](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)、[Skills](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/skills.md) 与 [Extensions](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/extensions.md)，并完成以下设计练习：

1. 为 `SkillRegistry` 写 Service Definition；分别设计 project、user、bundled providers；
2. Consumer 只依赖 registry capability，不 import 具体扫描器；
3. provider discovery 区分 `complete` 与 `incomplete`；扫描失败时保留 last-good state，但必须暴露 stale 状态；
4. plugin 注册的 tool、hook、resource 都返回 cleanup handle，卸载后不能留下幽灵能力；
5. 动态 extension 使用不可变 package version 和精确 run identity，升级不是原地覆盖正在运行的版本；
6. profile/bundle 只负责组合 plugin 与配置，不把业务逻辑重新塞回“大核心”。

Skills 采用三层渐进披露：

```text
Catalog：name + description + provenance
Candidate：匹配结果与选择理由
Definition：选中后才加载完整正文和资源
```

这与 [Codex Skills](https://developers.openai.com/codex/skills)及 [Claude Code Skills](https://code.claude.com/docs/en/skills)的按需加载思想一致。进一步要测：同名 skill 的 scope 冲突、cwd 改变后的 registry 更新、恶意 skill 请求越权、skill 文件热更新时正在运行的 task 是否固定版本。

### 这一阶段明确不做

- 不把所有类都改成 plugin；
- 不为了热更新牺牲可复现性；
- 不让 plugin 绕过 ToolExecutor、PolicyEngine 或 EventStore；
- 不把 MCP server 的工具描述直接当作可信权限声明；
- 不在没有 lifecycle/cleanup contract 前加载第三方代码。

### 退出条件

- 外部 Tool 与本地 Tool 使用同一内部 ToolCall/ToolResult 协议；
- Skill/MCP 的选择、注入和权限均可观测、可评测；
- 动态工具变化不会破坏正在运行的任务。

## 阶段 10：Multi-Agent

### 前置条件

只有单 Agent 已经具备以下能力，才进入 Multi-Agent：

- 稳定 Executor；
- workspace/sandbox；
- durable events；
- checkpoint；
- task/eval；
- context 与 budget；
- background task 生命周期。

否则，多 Agent 只会把单 Agent 的不稳定性并行放大。

### 学习重点

- 什么任务值得委派；
- 子任务是否真正独立；
- orchestrator 如何给出最小充分 context；
- sub-agent 的 workspace、branch/worktree 如何隔离；
- 状态、预算和权限如何继承；
- 结果如何验证和合并；
- 两个 Agent 修改同一文件怎样处理；
- 子 Agent 失败、超时、失联怎样恢复；
- 什么时候继续本地做比委派更便宜。

### DSH、Codex、Claude Code 对照研读：Delegation 是可选能力，不是第二个核心

DSH 的 [Subagent](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md)把 delegation 放在 capability seam 上，而不是写死进 agent loop。建议吸收：

- 多个 subagent provider 可以共存，能力描述必须准确；不支持 isolation、continuation 或 background 时要 fail loud；
- child session 持久化，active child runtime 只是进程内对象；
- parent/child lineage、delegation depth、预算和 authority 必须可追踪；
- tool filter 同时作用于 prompt visibility 和 execution lookup，不能“提示里隐藏但仍可调用”；
- 一个 child 使用单一 inbox queue 处理 follow-up/interrupt，避免并发写坏同一 session。

[Claude Code subagents](https://code.claude.com/docs/en/sub-agents)提供了另一个重要边界：子代理使用隔离 context；后台子代理遇到需要新增审批的操作会自动拒绝。Codex 的 worktree/subagent 思路则提醒我们把并行认知工作与并行文件副作用分开。

阶段实验必须加入 authority test：父 Agent 只有只读权限时，子 Agent 不得通过新 provider 获得写权限；child result 进入 parent 前必须附环境证据与 provenance。

### 实验顺序

1. 单 orchestrator + 单只读 researcher；
2. 两个只读 worker 并行分析不同模块；
3. 一个 worker 在隔离 worktree 修改代码；
4. orchestrator 验证并合并结果；
5. 多 worker 并行修改独立文件；
6. 冲突、超时、取消和预算耗尽实验。

### 对照评测

每个任务都比较：

```text
单 Agent vs Multi-Agent
```

至少观察成功率、耗时、token、冲突、重复劳动与最终 diff。没有可测收益，就不应保留复杂编排。

## 阶段 11：TUI、可观测性与项目化

### 学习目标

让用户看到需要做判断的信息，同时避免噪声、敏感信息与虚假确定性。

### TUI 应展示

- 当前任务和 plan；
- run 状态；
- 正在执行的 tool/background task；
- 精确审批请求；
- 关键 observation 摘要；
- 文件 diff；
- 测试结果；
- token/成本/耗时预算；
- blocker 和终止原因。

### DSH 与 Claude Code 对照研读：UI 和 Hook 都消费事件，不拥有真相

- DSH 的 Host/UI 从 live events 展示流式状态，从 durable session events恢复事实；不要从 stdout 文本反向猜 Agent 状态。
- Extension 可以有 Host 与 browser/UI 两半，但权限判断和执行仍留在 Host；UI 只是呈现与收集用户决策。
- [Claude Code Hooks](https://code.claude.com/docs/en/hooks)展示了丰富的生命周期插入点。minimal SWE Agent 不必复制全部事件，但应先稳定 `SessionStart/End`、`Pre/PostToolUse`、`PermissionRequest`、`Pre/PostCompact`、`SubagentStart/Stop`。
- Hook 分确定性 command hook 与 LLM-based judge；安全强制优先使用确定性 hook，LLM hook 只做补充判断且不能提升权限。

TUI 验收时做一次“重启重放”测试：关闭界面后只依赖 durable events 重建 plan、审批、tool results 和终止原因；live chunk 丢失不能改变最终事实。

### 不应默认展示

- 未经处理的密钥和环境变量；
- 无限滚动的完整 stdout；
- 不稳定的内部原始推理；
- 把模型自述当作环境事实；
- 与用户判断无关的 debug 噪声。

不要让系统依赖模型完整输出 `<thought>`。现代模型/API 可能只提供有限的 reasoning summary，Harness 应依赖结构化 action、plan、status 和环境证据，而不是隐藏思维链。

### 项目交付

- 架构图和模块职责；
- ADR（重要架构决策记录）；
- Tool/Executor/Policy 协议文档；
- threat model；
- benchmark 与回归报告；
- 真实 trajectory viewer；
- 失败案例分析；
- demo 视频；
- “为什么没有使用重型 Agent framework”的取舍说明。

目的：理解“极小 loop 为什么仍然有效”，防止为了架构漂亮过度设计。

- stopping；

### 第二站：DeepSeek Harness / Cordis

目的：研究“极小核心 + 可替换能力 + 可逆生命周期”怎样组成完整 Harness，同时练习识别哪些抽象适合当前项目、哪些属于规模化后才需要。

不要先逐包读源码。按问题沿官方文档和调用链阅读：

1. `docs/architecture.md`：plugin tree、三类事件、step/turn、session log；

每读一个 subsystem，写一张 seam card：

```text
Capability：解决什么失败模式
Definition：稳定协议和事件
Provider：至少两个可能实现
Consumer：谁依赖它
Lifecycle：start/stop/cleanup
Scope：global/project/session/agent/tool-call
Failure：缺失、部分可用、崩溃怎样表示
Adoption：现在采用 / 只做实验 / 延后 / 拒绝
```

警惕两种误读：一是把“everything is a plugin”理解成“每个类都必须插件化”；二是把 developer preview 的当前 API 当成标准答案。我们学习的是 seam、scope、lifecycle 和 event invariants。

### 第五站：OpenAI Codex CLI

目的：研究现代 coding agent 的运行时边界。

- background process；
- TUI 如何展示状态；
- 配置与项目指令。

```text
model 发出 shell call
→ 解析成内部事件
```

除源码外，专题阅读 [Codex `AGENTS.md`](https://developers.openai.com/codex/guides/agents-md)、[Skills](https://developers.openai.com/codex/skills)、[MCP](https://developers.openai.com/codex/mcp) 与 [Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security)，把“配置层、上下文层、权限层、执行层”分别画出来。

- Hook 事件和执行顺序；
- Hook、Skill、Subagent 各自适合的任务；
- deny-first 权限与 approval；
- project/user/managed 配置 scope；

- 防止 recursive hook/subagent loop。

### 第七站：MCP specification

目的：在实现 Skills/Plugins 之后理解协议边界，而不是先把 MCP 当魔法插件系统。

重点：

- Host / Client / Server；

- tools/resources/prompts；
- notification；

## 9. 贯穿全程的学习方法

每增加一项能力，必须完成六件事：

1. **定义问题**：当前失败案例是什么？
2. **定义边界**：新模块负责和不负责什么？
3. **先写协议**：输入、输出、状态、错误语义是什么？
4. **写测试/评测**：怎样证明它解决了问题？
5. **实现最小版本**：不同时加入相邻高级功能。
6. **对照复盘**：复杂度、成功率、成本和可维护性发生了什么变化？

建议每个阶段保留四类笔记，并遵守第 0 节文件名规范：

- `..._research_<topic>.md`：概念、外部系统解读与自己的解释；
- `..._architecture_<topic>.md` 或 `..._adr_<topic>.md`：接口、状态机、数据流与取舍；
- `..._experiment_<topic>.md` 或 `..._eval_<topic>.md`：任务、变量、指标和结果；
- `..._postmortem_<topic>.md`：失败轨迹、根因、修复与新增回归用例。

对任何外部 Harness 的学习笔记，都要把内容分成四栏：`事实（带源码/文档链接）`、`我的推断`、`拟采用设计`、`尚未验证`。这样不会把对 DSH/Codex/Claude Code 的观察误写成本项目已经具备的能力。

### 定期口试模板

每一阶段结束时，你应该能脱离代码回答：

1. 这一层解决的失败模式是什么？
2. 它的输入、输出和不变量是什么？
3. 正常、失败、超时、取消分别怎样表示？
4. 哪些事实来自模型，哪些来自环境？
5. 安全判断在哪里，强制边界在哪里？
6. 不实现这一层会怎样？
7. 怎样用数据证明这一层有效？
8. 现代开源 Agent 为什么可能采用不同设计？

## 10. 现在最优先的下一步

不要立刻实现 TaskPlanner、memory 或 multi-agent。

当前最优先的顺序是：

1. 冻结现有 Parser 重构成果；
2. 建立 Parser、Loop、Tool、Policy 的确定性测试；
3. 用 FakeLLM 建立端到端 loop 测试；
4. 修正 workspace/cwd、失败 observation、参数校验与异常边界；
5. 抽出 Executor；
6. 持久化完整 event trajectory；
7. 建立第一批 eval tasks；
8. 有了 baseline 后，再实验显式 Planning。

同时安排一个不改生产代码的 DSH 研究支线：

1. 先为现有 `ModelGateway / ToolExecutor / EventStore` 各写一张 seam card；
2. 选 `EventStore` 做第一次 provider-swap 设计实验，因为它副作用较可控、价值可测；
3. 写 ADR 回答“是否需要轻量 PluginHost”，在至少出现两个真实 provider 或一个真实卸载需求前，默认不实现；
4. 用现有 eval 比较重构前后行为，证明扩展性没有换来可靠性退步。

原因很简单：Parser 已经教会了你“模型意图怎样变成结构化 Action”；接下来必须学习 Harness 更核心的一半：

> 结构化 Action 如何被可靠、安全、可观察地执行，并用真实证据推动下一轮决策。

当你能用测试和 trajectory 解释一次任务为什么成功、为什么失败，并能在不信任模型输出的前提下限制真实副作用时，你才真正完成了 Agent Harness 的基础阶段。

## 11. 最终毕业标准

完成这条路线后，你不只是拥有一个“功能很多”的 Coding Agent，而应该能够：

- 从零实现一个可靠的 model–tool loop；
- 清楚划分 Model、Harness、Tool、Executor、Policy、Sandbox 和 UI；
- 设计易被模型正确使用的 ACI；
- 对 action、tool result、run state 和 event 建立稳定协议；
- 管理 token、时间、成本、进程和权限预算；
- 用 checkpoint、session 和 memory 支持不同生命周期；
- 用 eval 而不是主观 demo 判断架构改动；
- 阅读现代开源 Agent 时追踪完整数据流；
- 解释为什么某项能力现在需要，为什么另一些能力应当延后；
- 用失败案例、测试、指标和架构取舍展示自己的工程深度。

这才是“从马车到高铁”的真正含义：不是把所有现代名词塞进项目，而是理解每一节车厢为什么存在、它连接在哪里、失效时会发生什么，以及如何证明整列车比原来跑得更稳。
